# 多通道提交超时与版本查询优化

日期：2026-11-17。负责人已批准实施；重点是多通道共用逻辑，兼顾版本查询速度。保留既有未提交改动，不操作真实设备、不调用真实模型/平台、不提交或打包。

## 已确认原因

`AiBatchService.submit`持会话锁调用`send`，完全访问权限检查经`target_current`等待GUI；聊天刷新读取草稿也需要会话锁，GUI无法领取请求，20秒后超时。当前隔离回归加载HEAD旧提交方法可稳定失败，新实现通过。现场当时无线程栈，不排除其它阻塞。

## 实施边界

1. GUI/权限预检在会话锁外，统一发送入口在锁内复核数据快照、取消标记、运行状态和队列容量，绑定本次批量请求；失败恢复自己的状态和批量参数。消费者在同一锁下确认入队令牌，持久化失败的队列票据不执行。
2. 不搬迁已有GUI/设备引擎，不提高并行度，不延长排队超时；超时消息补动作代码、等待时间和未领取状态，批量会话日志显示真实通道集合。
3. 独立版本编排模块识别完整明确请求；数量不符/无效/重复目标澄清，复杂/历史/否定请求沿用原模型路由。明确请求走现有受控`device.version`与Job及三档权限，不模拟GUI、不改变登录/锁源/命令。
4. 单台异常继续其余目标；逐台开始前复核目标和登录配置，配置变化或业务取消后剩余不执行。逐台事件及终态返回结构化结果，保留已有成功字段。
   `CapabilityAuthority`追加可选`target_endpoints`，只由可信会话快照构造，版本准入与执行初始校验通道/源IP/目标IP/端口，封住最后一次权限检查后配置切换的窗口；模型参数不能提供或覆盖此绑定，原GUI无绑定调用保持兼容。
5. 现有后台会话worker独立观察已准入Job，模型停止不传递为业务停止，结果继续回到原会话。先真实结果表，再用本轮结构化结果调用一次无工具模型说明；说明失败不改业务结果。维持现有对话串行规则。
6. 在准入前保存可信operation关联，启动后只按原身份/operation查询原Job，结果投影去重，不重放设备操作或AI说明；已持久化逐台事件在中断后仍保留。
