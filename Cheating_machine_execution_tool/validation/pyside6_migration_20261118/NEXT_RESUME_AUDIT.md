# 失败轮次续跑迁移审计

运行中与批次后单通道入口的实施结果见[续跑阶段报告](RESUME_QT_REPORT.md)。下文记录实施前审计。

旧入口位于 `src/ui/power_test_resume_menu.py`。操作员右击失败通道，确认保留已完成轮次并从下一轮继续。`PowerTestResumeSession.can_resume` 判定通道是否失败、线程是否退出、是否有恢复任务或停止请求。原 `submit` 负责重复保护，原 `_validate` 负责配置指纹和版本预检。三项基准全空时跳过，部分填写时拦截，全部填写时严格比对目标样机。独立续跑继续跳过初始化断电。

## Qt 尚缺的行为

| 场景 | 当前代码 | 迁移所需证据 |
| --- | --- | --- |
| 原批次运行期间续跑 | `PipelineOrchestrator` 在旧测试启动前把会话放入 `PipelineProjection`，`DeviceCapabilities.latest_aging` 只在编排结束后赋值。Qt 的通道快照暂未读取仍在运行的会话。 | Qt 能在原批次持有电源和目标资源时，向同一会话提交已就绪的一条失败通道。复用现有子进程控制队列，验证其它通道和原停止语义。 |
| 原批次结束后续跑 | 原 `aging.resume` 已处理同身份父任务、范围和资源准入。Qt 没有确认入口。 | 只认本进程原批次及其目标快照，确认完成轮数与总轮数，重新校验项目配置与资源，保留原结果后显示独立恢复状态。 |
| 原进程退出与恢复交叠 | `PowerTestResumeSession` 在控制队列未接单时可等待原串口释放，再走独立恢复。`CapabilityJobs` 在 runner 返回后释放任务的资源。 | 覆盖待续跑命令与原进程退出交叠时的资源和日志归属。Qt 应在原会话结束前保持所有权，防止资源释放后旧任务自行启动，或与另一项目发生重叠。 |
| 结果与停止 | 会话回调仍指向父任务 `PipelineProjection`。Qt 的 `poll` 在已完成 Job 的事件读完后标记为已排空。 | 复用原回调的绝对轮次和尝试隔离，续跑事件仍可见。原全流程结论、已完成轮数和其它通道结果继续保留；全局停止等待实际续跑收尾。 |

## 实施范围

入口以 `ProjectDetail` 通道矩阵和列表为主，支持右键操作，可从现有通道快照辅助发现。界面只显示由原会话投影的可续跑通道，提交前重新核对同一项目、父任务、会话标识、通道、轮次及配置。切换项目或关闭窗口不能重定向待确认动作。

先在 Qt 控制面和 `PipelineProjection` 的 GUI 专用接点验证双路径，保持 `PowerTestResumeSession`、旧 IPC、电源控制、版本判据和现有通用能力。若需要变更原设备业务的资源释放、运行状态或停止逻辑，应在这一步停下，列出行为差异和回退边界，由负责人确认。

已执行 `python scripts/run_tests.py test_power_test_resume test_legacy_power_initialization -v`，33 项原行为用例通过。覆盖运行中控制队列接入、退出竞争单次回退、同一串口所有者锁、版本异常拦截、停止和不初始化断电。本次属于下一项的原代码审计，Qt 控制面尚待实施，真实设备复验等待负责人授权。

## 批次结束后的等待队列审计

实施结果见[排队阶段报告](RESUME_QUEUE_QT_REPORT.md)。

现有 Qt 主窗口一次只准入一个设备任务，原后置续跑内部可接收多个通道，但会在同一个设备进程锁上串行等待。不能把第二个通道直接送入原会话，同时仍只为第一条持有通道和网卡资源。后续需要在 Qt 工作区后台按同一原批次保留已确认请求，前一条释放后重新执行原单通道准入。等待项用实际申请信息呈现，只有原服务开始后才显示为运行。

覆盖同一批次不同通道多次确认、相同通道去重、前一条成功或失败后安全衔接、版本／网卡变化阻止未开始通道、已请求全局停止或关闭时清空等待项，以及前一条结束与后一条开始之间其它启动入口的保护。保留旧 Tk 的原进程锁、设备代码和历史；软件重启后等待项不得自动执行。
