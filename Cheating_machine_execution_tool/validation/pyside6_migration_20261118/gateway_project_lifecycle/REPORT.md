# Qt 项目关闭与网关消息回执

本批对应迁移计划 Phase 5 的多项目网关和 Phase 6 的任务生命周期。审计从原 `GatewayInstanceClient` 的网络线程、收件箱线程追到 `WorkspaceGatewayBridge`、`WorkspaceService` 和 Qt 工作区。网络线程负责收取请求和回复持久化回执，收件箱线程负责将已接收请求交给对应项目。两个线程可能同时访问同一个项目。

## 已复现的差异

在两个临时项目和模拟传输服务中，让 A 的接收线程停在写回执前，再让同一项目的收件箱处理结束。原路由器此时报告 A 可以关闭，尽管接收线程尚未返回。该失败由事件同步复现，B 使用另一收件箱。另沿实际 Qt 退出入口核对，旧工作区先要求平台已空闲，随后才调用原平台的停止接口。对按停止请求进入空闲的活动客户端，这个顺序无法完成退出。[原路由器失败断言](before.txt)

## 修改与验证

另在原 Qt 源码窗口模拟了仍在运行的飞书传输服务。点击关闭后，旧工作区返回“关闭未完成”，传输服务没有收到停止请求。修正后的窗口保持可见，项目仍打开；模拟服务报告空闲后，工作区再释放项目和窗口。[原生窗口修正前的实际结果](native-close-before.txt)

- `src/services/workspace_gateway.py` 按项目记录正在接收和正在处理的请求。在接收回执写入、返回失败或处理线程退出时，分别释放该次使用。关闭期间拒绝新转发，项目列表只列可接收请求的项目。保留原请求 ID、已落盘的结果、未知回执以及原授权范围。
- `src/services/qt_workspace_adapter.py` 从原工作区请求停止接入，等待客户端回报空闲；项目的收件箱仍在使用时，保留项目、会话及数据。离开工作区或单独关闭 A 时分别等待各自的收尾。已确认的挂测停止继续交给原执行器。
- `tests/test_workspace_gateway.py`、`tests/test_qt_workspace_adapter.py` 和 `tests/qt_workbench_probe.py` 覆盖 A 双线程交错、B 独立运行、收件失败与去重、关闭项目和工作台，以及真实 Qt 窗口发出关闭请求后等待模拟平台完成。

为隔离上一候选的构建输入，先将源码复制到临时目录，使用标准测试入口、脱敏配置和 Windows 私有桌面验证。14 项原路由及远程权限专项、7 项 Qt 项目关闭相关用例和 1 项真实窗口关闭用例通过。[路由与权限](isolated.txt) · [工作区关闭](qt-shutdown.txt) · [原生窗口](native-close-focused.txt)

此批验证使用临时数据库、合成消息和模拟客户端。没有向外部平台发送消息，没有操作 DUT。Qt 按已保存槽位自动装配项目会话及实例客户端、真实平台接入、实体设备和长期挂测仍需单独验证。本阶段沿用工作台已有的退出界面，未增加新的设计页面；原 Tk 入口和原测试配置仍可用。
